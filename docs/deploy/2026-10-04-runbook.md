# Runbook: v1-omnikon → v2-curiousparc on itcguard.duckdns.org (4 Oct 2026)

Upgrades the EC2 box (t3.micro, ap-south-1, `~/itc-guard`, Docker Compose + Caddy)
from tag `v1-omnikon` to tag `v2-curiousparc` (main after merging `phase2-demo`).
Demo is 5 Oct. Run the blocks in order, one at a time, and read each check before going
on. Rehearsed end to end on a laptop against `docker-compose.prod.yml` (old stack with
pooled visitor orgs → upgrade → smoke → rollback) before being written down.

**Rehearsal (laptop, 4 Oct):** a v1 stack with 2 POOL + 3 CLAIMED seeded orgs and an org
1 → steps 1–10 → rollback. Backup 2.8 MB gzipped, 14 tables; 8 migrations applied; 5
workspaces purged, org 1 untouched; smoke 149/149; rollback back to `007` with v1 serving.
(On Git Bash for Windows, `/app/...` paths need `MSYS_NO_PATHCONV=1`; not on the server.)

**Downtime:** from step 6 (`dc stop api`) to step 8, about 2 minutes. Everything before
step 6 runs while v1 keeps serving.

**Rollback points:** before step 6, nothing on the live stack has changed: `git checkout
v1-omnikon` and stop. From step 6 on, use [Rollback](#rollback) at the end.

---

## 0. Connect and set up the shell

Connect the way you normally do (DEPLOY.md uses SSM):

```bash
aws ssm start-session --target <instance-id>
sudo su - ubuntu
```

or `ssh -i <key>.pem ubuntu@itcguard.duckdns.org` if port 22 is open for you. Then, in the
same shell (everything below assumes it):

```bash
cd ~/itc-guard
alias dc='docker compose -f docker-compose.prod.yml --env-file .env.prod'
STAMP=$(date +%Y%m%d-%H%M); mkdir -p ~/backups; chmod 700 ~/backups; echo "STAMP=$STAMP"
```

**Write the STAMP down.** The rollback needs it if the shell is lost.

Pre-flight:

```bash
free -h && df -h / && docker system df
dc ps
git status --short && git describe --tags --always
```

Check: 4 services Up; `git describe` says `v1-omnikon`; `git status` prints nothing
(`.env.prod` is gitignored). At least **2 GB free** on `/` (two new images plus build
cache). If not: `docker image prune -f && docker builder prune -f`, then re-check. Swap
should show 2.0Gi; if it shows 0B, do DEPLOY.md step 2 first.

```bash
dc exec -T db sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N "$MYSQL_DATABASE" -e "
  SELECT COUNT(*), MAX(filename) FROM schema_migrations;
  SELECT COALESCE(demo_state, \"(app org)\") AS state, COUNT(*) FROM organizations GROUP BY demo_state;"' 2>/dev/null
```

Check: `7  007_demo_tenancy.sql`. The second query counts the old visitor orgs that step 7
deletes. Note the numbers.

## 1. Back up the database

```bash
BACKUP=~/backups/itc_guard-$STAMP-v1.sql.gz
dc exec -T db sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --quick \
  --routines --triggers --no-tablespaces --databases "$MYSQL_DATABASE"' 2>/dev/null | gzip > "$BACKUP"
ls -lh "$BACKUP"
zcat "$BACKUP" | tail -1
zcat "$BACKUP" | grep -c '^CREATE TABLE'
```

Check, all three:
- size is not tiny: an empty schema is ~5 KB; with org 1 and some visitor orgs expect
  hundreds of KB to tens of MB gzipped;
- the last line is `-- Dump completed on 2026-10-...`;
- `14` tables (13 app tables + `schema_migrations`).

If any fails, stop: do not go on without a backup. Keep the old environment file next to it:

```bash
cp .env.prod ~/backups/env.prod-$STAMP-v1 && chmod 600 ~/backups/env.prod-$STAMP-v1
```

## 4. Update `.env.prod`

Variables are names only here; no value is printed. `setenv` replaces a line or appends it.

```bash
setenv() { if grep -q "^$1=" .env.prod; then sed -i "s|^$1=.*|$1=$2|" .env.prod; else echo "$1=$2" >> .env.prod; fi; }

# removed: the seeded warm pool is gone
sed -i '/^DEMO_POOL_SIZE=/d; /^DEMO_SESSION_HOURS=/d; /^DEMO_SEED_CONCURRENCY=/d' .env.prod

# added / changed
setenv SITE_ADDRESS itcguard.duckdns.org
setenv DEMO_TENANCY on
setenv DEMO_COOKIE_SECURE true
setenv DEMO_SESSION_DAYS 180
setenv DEMO_RETAIN_DAYS 30
setenv DEMO_MAX_ORGS 200
setenv DEMO_IDLE_MINUTES 180
setenv DEMO_SWEEP_MINUTES 5
setenv DEMO_SESSION_SECRET "$(openssl rand -hex 32)"
```

Check, without printing secrets:

```bash
grep -E '^(SITE_ADDRESS|DEMO_[A-Z_]+|MATERIALITY_TOLERANCE_PAISE)=' .env.prod | sed -E 's/^(DEMO_SESSION_SECRET)=.*/\1=(set)/'
grep -c '^DEMO_SESSION_SECRET=' .env.prod
awk -F= '/^DEMO_SESSION_SECRET=/{print length($2)}' .env.prod
```

Expect: no `DEMO_POOL_SIZE` / `DEMO_SESSION_HOURS` / `DEMO_SEED_CONCURRENCY`; the eight
values above; the secret line **once**, **64** characters. `DB_*`, `HTTP_PORT`,
`HTTPS_PORT`, `ACME_EMAIL` and the `*_MEM_LIMIT` / `API_NODE_OPTIONS` lines are unchanged
and must stay as they are (the MySQL volume was initialised with those DB passwords).

The new secret invalidates every v1 cookie on purpose: those cookies name the visitor orgs
that step 7 deletes, so every visitor starts with a fresh, empty workspace.

`MATERIALITY_TOLERANCE_PAISE` is new and optional: leave it unset (engine default ₹1).

## 5. Build the new images (v1 still serving)

One service at a time, watching memory. In a second session, optionally: `watch -n2 free -h`.

```bash
free -h
dc build api
free -h
dc build web
docker images 'itc-guard-prod-*'
```

Check: both builds end with `Built` / `naming to docker.io/library/itc-guard-prod-...`;
`latest` of api and web now have new IMAGE IDs, and the `v1-omnikon` tags kept the old
ones. The api build regenerates the fixtures and takes a few minutes on a t3.micro. If a
build is killed (exit 137 / "cannot allocate memory"): `dc stop web` (the old static site;
v1's API keeps answering but the page will not load, so be quick), re-run the failed build,
then go on to step 6, which starts the new web anyway.

Do **not** build `db`: `deploy/mysql` is unchanged, and leaving its image alone means
`dc up` will not restart MySQL.

## 6. Stop the API and run migrations 008–015 from the new image

The site's API is down from here until step 8.

```bash
dc stop api
dc run --rm api node src/db/migrate.js
```

Expect, in this order:

```
[db] migrating itc@db:3306/itc_guard  [...]
skip  001_init.sql  …  skip  007_demo_tenancy.sql
apply 008_claimable_split.sql
apply 009_supplier_scheme_source.sql
apply 010_supplier_gstin_aliases.sql
apply 011_workspace_clock.sql
apply 012_upload_snapshots.sql
apply 013_supplier_contacts.sql
apply 014_cross_period_links.sql
apply 015_workspace_gstin.sql
applied 8 migration(s)
```

If it stops at `001_init.sql was already applied but its contents changed`, **nothing
was applied** (it checks every applied file before applying any): the server's checkout
does not match git byte for byte. Bring v1 back without touching the database:

```bash
git checkout v1-omnikon
docker tag itc-guard-prod-api:v1-omnikon itc-guard-prod-api:latest
docker tag itc-guard-prod-web:v1-omnikon itc-guard-prod-web:latest
dc up -d --no-build
```

(The rehearsal hit exactly this from a Windows checkout with `core.autocrlf`. A Linux
clone checks out the same bytes for v1 and v2, and v1 → v2 does not change 001–007.)

If an `apply` fails, stop and go to [Rollback](#rollback): the database is restored from
the backup, so a half-applied migration does not matter.

## 7. Delete the old visitor workspaces (never org 1)

The v1 pool and any visitor org seeded in the last 30 days would otherwise survive the
reaper (seeded orgs carry uploads, and a workspace with an upload in `DEMO_RETAIN_DAYS` is
kept) and count against the cap. Org 1 has `demo_state` NULL and is never listed; the tool
refuses it by id as well.

```bash
dc run --rm api node /app/tools/purge-visitor-workspaces.js --all
dc run --rm api node /app/tools/purge-visitor-workspaces.js --all --yes
```

Check: the first lists the workspaces and says `N would be deleted` (N = the visitor count
from step 0); the second ends `deleted N of N; 0 visitor workspace(s) left`.

Raw-SQL fallback (same deletes, same order, one transaction) in the
[appendix](#appendix-the-purge-in-sql).

## Rollback

Restores v1 code, v1 images and the step-1 database. Visitor activity since step 1 is
lost, which is only the old visitor workspaces step 7 deleted anyway.

If the shell is new, set it up again (step 0's `cd` and `alias`), and set `STAMP` to the
value you wrote down:

```bash
STAMP=<the value from step 0>
BACKUP=~/backups/itc_guard-$STAMP-v1.sql.gz; ls -lh "$BACKUP" ~/backups/env.prod-$STAMP-v1
```

```bash
dc stop api web
git checkout v1-omnikon
cp ~/backups/env.prod-$STAMP-v1 .env.prod

# the database, exactly as backed up (the dump recreates it)
dc exec -T db sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "DROP DATABASE $MYSQL_DATABASE"' 2>/dev/null
zcat "$BACKUP" | dc exec -T db sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' 2>/dev/null
dc exec -T db sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N "$MYSQL_DATABASE" -e "SELECT COUNT(*), MAX(filename) FROM schema_migrations"' 2>/dev/null

# the v1 images, no rebuild
docker tag itc-guard-prod-api:v1-omnikon itc-guard-prod-api:latest
docker tag itc-guard-prod-web:v1-omnikon itc-guard-prod-web:latest
dc up -d --no-build
dc ps
curl -s https://itcguard.duckdns.org/health; echo
curl -s https://itcguard.duckdns.org/api/session | head -c 300; echo
```

Check: `7  007_demo_tenancy.sql`; four services healthy; `/api/session` answers. The
app user keeps its grants across the DROP (MySQL keeps database-level privileges), which
the rehearsal confirmed.

If the `v1-omnikon` image tags are gone for any reason, replace the two `docker tag`
lines and `--no-build` with `dc up -d --build` (rebuilds v1 from the checkout).

## Appendix: the purge in SQL

Only if the tool in step 7 cannot run. After migrations (it names tables 010 and 013
create). Org 1 is excluded twice: by id and by `demo_state IS NOT NULL`.

```bash
dc exec -T db sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' 2>/dev/null <<'SQL'
START TRANSACTION;
CREATE TEMPORARY TABLE purge_orgs AS
  SELECT id FROM organizations WHERE demo_state IS NOT NULL AND id <> 1;
SELECT COUNT(*) AS deleting FROM purge_orgs;
DELETE FROM match_results          WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM runs                   WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM record_changes         WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM supplier_periods       WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM supplier_risk          WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM supplier_gstin_aliases WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM suppliers              WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM supplier_contacts      WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM expected_rate_lines    WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM expected_invoices      WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM portal_rate_lines      WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM portal_records         WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM uploads                WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM users                  WHERE org_id IN (SELECT id FROM purge_orgs);
DELETE FROM organizations
 WHERE id IN (SELECT id FROM purge_orgs) AND demo_state IS NOT NULL AND id <> 1;
COMMIT;
SELECT COALESCE(demo_state, '(app org)') AS state, COUNT(*) FROM organizations GROUP BY demo_state;
SQL
```
